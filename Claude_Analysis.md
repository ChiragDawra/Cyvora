# ThreatMap: A Feasibility & Strategy Report for a Student-Built Threat-Intel Dashboard

## TL;DR
- **Build it — but rebrand from "prediction engine" to an honest "open threat-intelligence aggregation and anomaly-flagging dashboard," and let the AWS/DevOps engineering be the resume star, not the ML.** The data-ingestion + cloud pipeline is highly achievable and directly builds your Cloud/DevOps identity; the ML "prediction" and "geospatial origin attribution" claims as written are the parts most likely to read as fake to a sharp interviewer and must be scoped down.
- **Two of the five listed ML components are credibly achievable (time-series anomaly detection, clustering), one is achievable by reusing MITRE's own tool (ATT&CK tagging via TRAM), one is defensible only with honest baselines (LSTM forecasting), and one is technically wrong as stated (IP geolocation ≠ attacker "origin attribution").** CISA itself states you cannot identify the true physical location of an attacker from IP geolocation alone.
- **The differentiation story is strong if you position against the "attack maps are theater" critique** — Norse Corp's viral map, debunked by Brian Krebs in 2016, was honeypot "eye candy." Your edge is *transparency, real cited open feeds, MITRE mapping, and reproducible methodology*, not prettier arcs.

## Key Findings

### Data sources are the easiest, most defensible part — but almost all now require a free key and are non-commercial
Every core feed is free for a student/non-commercial project, but the terms and quotas matter:

- **abuse.ch (URLhaus, ThreatFox, Feodo Tracker, MalwareBazaar, SSLBL):** As of mid-2025, **all abuse.ch APIs require a free `Auth-Key` header** (sign up at auth.abuse.ch); authentication became mandatory June 30, 2025. Free "under fair use principles"; commercial/for-profit use may require a paid tier. URLhaus full DB dumps regenerate every 5 minutes (don't poll faster); country/ASN/TLD feeds every 10 minutes. This is your best real-time, high-volume, structured source (malicious URLs, botnet C2 IPs, malware IOCs with tags and malware-family labels).
- **AlienVault OTX (LevelBlue):** Free API key after signup + subscribing to ≥1 pulse. Provides "pulses" — structured IOC collections with context, MITRE ATT&CK mappings, targeted countries, and industries. Also exposed via STIX/TAXII. Ideal for the MITRE mapping and "target industry" angle. Community/free tier is generous; no hard published numeric limit for reasonable use.
- **Shodan:** The main API is NOT free — free accounts get no API credits; Membership is a one-time $49; the Freelancer plan is $69/mo for 10,000 query credits (Small Business $359/mo, Corporate $1,099/mo). **Use the free `InternetDB` API instead** (`internetdb.shodan.io`) — no key, unauthenticated, higher rate limit, returns open ports, CPEs, hostnames, tags, and known CVEs per IPv4; refreshed weekly; free for non-commercial use only. Also `CVEDB` (no key, updated daily) for CVE/KEV/EPSS lookups. This sidesteps the cost problem entirely.
- **AbuseIPDB:** Free account = **1,000 checks/reports per day** (verified webmaster 3,000/day, supporter 5,000/day); key in `Key:` HTTP header, JSON responses, HTTPS only; same-IP re-report throttled to once per 15 min. Great for IP reputation enrichment and abuse categories/confidence scores.
- **GreyNoise Community API:** Free but heavily limited — the docs show unauthenticated users get **10 IP lookups per day**; a free registered account key raises this to a few thousand/day. Returns only noise/RIOT/classification (no tags/metadata/context on the community tier — that's enterprise). Use for spot enrichment, never bulk ingestion.
- **CISA KEV:** Fully free public JSON feed, **no key, no auth** (`cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`). Highest-signal vulnerability data (only actively-exploited CVEs, with vendor/product/date-added/due-date). CISA adds entries irregularly, several times per week; poll daily and diff. Zero friction — include this.
- **NVD CVE API 2.0:** Free; **without key = 5 requests per rolling 30 s; with a free key = 50 requests per 30 s.** NIST recommends the incremental `lastModStartDate`/`lastModEndDate` pattern and sleeping ~6 s (2 s with key) between calls, updating no more than every 2 hours. Good for CVE enrichment/metadata.
- **Others worth adding cheaply:** URLhaus + Feodo already give you velocity; free MISP feeds (CSV/JSON), CIRCL, and Spamhaus DROP lists exist but add integration overhead. Don't over-collect.

**Realistic combined volume a solo dev can ingest continuously:** Comfortably a few hundred thousand IOCs/day if you (a) poll dump/blocklist endpoints on schedules (every 5–15 min for abuse.ch, daily for KEV/NVD/InternetDB) rather than doing per-IP lookups, and (b) reserve the rate-limited per-lookup APIs (AbuseIPDB 1k/day, GreyNoise ~10/day unauth, NVD 50/30 s) for *enrichment of a filtered subset*, not the firehose. The single biggest ingestion trap is trying to enrich every IP through a 1,000/day or 10/day endpoint — that dies instantly. Architect "bulk dumps for volume, per-lookup APIs for a curated shortlist."

### Realistic ML scope: two solid, one reuse-don't-build, one defensible-with-caveats, one "reframe it"
Ranked by how credibly a non-specialist student can deliver them:

1. **Time-series anomaly detection on feed volume — ACHIEVABLE and the best ROI.** Aggregate daily/hourly counts per category (malware family, port, country, ATT&CK technique) and flag statistical spikes. Use `statsmodels`/STL decomposition, **Prophet**, or **PyOD** (scikit-learn-style `fit`/`predict` API, 60+ detectors, 46M+ downloads, benchmark-backed). Genuinely useful and honestly describable as "statistical anomaly detection" — not overclaimed.
2. **Clustering attack signatures (DBSCAN/K-means) — ACHIEVABLE.** scikit-learn DBSCAN groups IOCs by features (ports, ASN, malware tag, geo) without pre-setting the cluster count (it needs only epsilon + minPoints). Defensible as unsupervised exploratory grouping; keep feature engineering honest and explainable.
3. **MITRE ATT&CK technique classification (NLP) — ACHIEVABLE by reusing MITRE's own tool, not building from scratch.** Use **TRAM (Threat Report ATT&CK Mapper)**, MITRE Center for Threat-Informed Defense's open-source project (Apache-2.0, Docker/Kubernetes deployable). Per MITRE's Jon Baker, its current model was trained by "annotat[ing] 150 reports containing 4,070 technique-labeled sentences out of 19,011 total samples," uses a fine-tuned **SciBERT** model (also shipped as a Jupyter notebook), and classifies the **50 most prevalent ATT&CK techniques** (of ~625). Do NOT train your own ATT&CK classifier from zero — run TRAM on OTX pulse/report text. This yields a real, citable, credible NLP component.
4. **LSTM next-attack-vector prediction — DEFENSIBLE ONLY WITH HONEST BASELINES; overclaimed as written.** The forecasting literature is decisive: **Makridakis, Spiliotis & Assimakopoulos (2018, PLOS ONE)** found ML methods including LSTM/RNN were "dominated" by eight statistical methods across all accuracy measures and horizons on the M3 series ("the one-step-ahead accuracy of the best ML method … was lower than that of the worst statistical one"). The **M4 Competition (2018, Int. J. Forecasting)** reported "the six pure ML methods performed poorly, with none of them being more accurate than the combination benchmark and only one being more accurate than Naïve2." On short, noisy, univariate daily counts (exactly your case), ARIMA/Prophet/seasonal-naïve routinely beat LSTM. There IS genuine cyber precedent — **Fang et al. (2019), EURASIP Journal on Information Security, "A deep learning framework for predicting cyber attacks rates"** (bidirectional BRNN-LSTM) — but it forecasts *attack rates/volume*, not "which vector spikes next," which is largely unproven. **Recommendation:** implement it as "spike-likelihood per category" and ALWAYS report LSTM alongside ARIMA/Prophet/seasonal-naïve with honest error metrics. Never market it as reliable prediction.
5. **Geospatial ML for origin attribution — TECHNICALLY WRONG as stated; reframe.** **CISA Alert AA20-198A** (with Palo Alto Networks and IBM) states plainly: *"it is not possible to identify the true physical location of malicious activity based solely on the geolocation of Internet Protocol (IP)."* VPNs, residential/SOCKS proxies, VPS/network tunnels, botnet-compromised hosts, and IP spoofing all break the IP→origin link (also echoed by Australia's ASD/ACSC). **Reframe as "geolocation of malicious infrastructure / exit nodes"** — an honest visualization — and explicitly foreground the attribution limitation. Done well, this candor becomes one of your strongest interview signals of security maturity.

**Datasets for training/validation:** CICIDS2017 (Canadian Institute for Cybersecurity, UNB; Sharafaldin et al., 2018 — note heavy benign class imbalance), UNSW-NB15 (Moustafa & Slay, 2015), and NSL-KDD (Tavallaee et al., 2009) for labeled attack traffic; MITRE ATT&CK STIX data + TRAM's annotated corpus for technique tagging; and your own accumulated feed history for the time-series work.

### Architecture & AWS stack (this is your real resume win)
A concrete, buildable, mostly-serverless design that maps cleanly onto AWS Cloud Practitioner concepts and builds legitimate DevOps experience:

- **Scheduled ingestion:** **EventBridge Scheduler → Lambda** functions per feed (Python), one schedule per cadence (5–15 min for abuse.ch; daily for KEV/NVD/InternetDB). Canonical serverless pattern.
- **Raw landing + normalization:** Land raw pulls in **S3**; a normalizer Lambda maps each feed's fields into a common STIX-like IOC schema and writes to the operational store (optionally EventBridge Pipes as no-code glue).
- **Databases:** **DynamoDB** for the current IOC/alert store (25 GB always-free) with time/geo GSIs; **S3 + Athena** for cheap historical/time-series analytics. **Avoid Timestream — Timestream for LiveAnalytics closed to new customers on June 20, 2025**, so a new student account cannot provision it; if you want a purpose-built TSDB use Timestream for InfluxDB, or just Postgres/RDS. For "graph-like" attack relationships, keep it simple: adjacency records in DynamoDB or Postgres, not a dedicated graph DB.
- **ML serving:** Do NOT reach for SageMaker (cost/complexity). Run scikit-learn/PyOD/Prophet inside a Lambda or a small scheduled **Fargate** task; persist outputs (anomaly scores, clusters, forecasts) back to DynamoDB. TRAM runs containerized (Docker) — a clean ECS/Fargate showcase.
- **API + frontend:** **API Gateway → Lambda** backend; **React/Next.js** frontend (plays to your existing strength) served via **S3 + CloudFront**. Globe via **globe.gl / react-globe.gl** (Three.js/WebGL wrapper with declarative arcs + points layers) — but ship a **2D map (deck.gl or Leaflet) fallback** and be ready to argue the globe is UX, not analysis.
- **Alerting/subscription:** **SNS** (email/SMS) or a Lambda posting to a webhook; store user IP-range subscriptions in DynamoDB and match new IOCs against them.
- **The DevOps layer that actually earns the resume line:** **Terraform (or CloudFormation/CDK) for all infra as code; GitHub Actions CI/CD** (lint/test/deploy); **Docker** for the ML/TRAM service; **CloudWatch** dashboards, metrics, alarms, structured logs; IAM least-privilege; an **AWS Budgets** alarm to protect the free tier. This converts "a security dashboard" into "I designed, provisioned, and operated a cloud-native, IaC-managed, CI/CD-deployed data pipeline."

### Differentiation: lead with honesty, not lasers
The landscape is crowded with *vendor-telemetry* maps, each showing a curated slice of its own footprint:
- **Kaspersky Cyberthreat Real-Time Map** — endpoint/AV telemetry, visually the most polished, but skewed toward Kaspersky's customer base (heavy in Eastern Europe/Asia).
- **Fortinet FortiGuard** — per FortiGuard Labs materials, telemetry from **5.6M+ sensors deployed globally** plus 500+ researchers across 25 countries.
- **Digital Attack Map** (Arbor Networks + Google Ideas) — "powered by data fed from **270+ ISP customers worldwide** who have agreed to share anonymous network traffic and attack statistics," with history back to June 2013 (Krebs, KrebsOnSecurity, 2015); DDoS only.
- **Check Point ThreatCloud**, **Bitdefender**, and the (non-map) analysis tool **MITRE ATT&CK Navigator**.

Two facts to weaponize in your positioning:
- Practitioners openly call these maps theater. A 12-year threat-intel/IR practitioner writes: *"these maps are theater, not truth. They're not fake—but they're dangerously incomplete… Live cyber attack maps are symptom trackers—not diagnostic tools."*
- The cautionary tale is **Norse Corp**. Brian Krebs (Jan 2016) called its viral map "serious eye candy: It purported to track the source and destination of countless Internet attacks in near real-time." Norse claimed 8M+ honeypot "sensors" in 47 countries; critical-infrastructure expert **Robert M. Lee** showed its headline Iran "attacks" were merely scans against Norse-run honeypots that "cannot be accurately used for attribution." Norse imploded in 2016.

**Your differentiation is therefore NOT "another globe."** It is: (1) **100% transparent, cited open-source feeds** anyone can reproduce; (2) **MITRE ATT&CK technique mapping** on ingested reports (most public maps don't do this); (3) **honest methodology** — you explicitly show what the data can and cannot claim (no fake attribution, spikes labeled experimental); (4) **free and self-hostable**, filling the "good free threat-intel dashboard" gap the vendor tools lock behind enterprise sales.

### Resume & interview positioning
Frame the SAME project two ways depending on the role. Track and report real metrics: feeds integrated, records/day ingested, pipeline latency (feed→dashboard), uptime, anomaly-detection precision on a back-tested split, TRAM technique-tagging coverage, infra fully in Terraform (resource count), CI/CD deploy time, and monthly cloud cost (near-$0 on free tier).

**Cloud/DevOps framing (primary):** *"Designed and operated a cloud-native threat-intelligence pipeline on AWS ingesting N open feeds (~X00k IOCs/day) via EventBridge-scheduled Lambdas into DynamoDB/S3; fully provisioned with Terraform, containerized ML service on Fargate, CI/CD via GitHub Actions, monitored with CloudWatch alarms — running at ~$Y/month on the free tier."*

**AI/ML framing (secondary):** *"Built anomaly-detection and MITRE ATT&CK technique-tagging over live threat feeds using PyOD/Prophet and MITRE's TRAM (SciBERT) model, benchmarking LSTM volume forecasts honestly against ARIMA/Prophet/seasonal-naïve baselines."*

**Likely interview questions this opens** (and how to be ready): serverless vs. containers tradeoffs; rate-limit handling, idempotency, retries, dead-letter queues; DynamoDB single-table data modeling and access patterns; Terraform state management; how you'd scale ingestion; how your anomaly detector controls false positives; "why LSTM vs ARIMA?" (answer: on short univariate counts it often shouldn't be — cite Makridakis/M4 and show your baselines); and the one you must ace — **"how do you know the attack really came from that country?"** (answer: you don't, and here's why, citing the CISA geolocation/attribution limitation). For any mocked/simplified part, say so plainly and explain the credible version you'd build with more time — interviewers reward that over bluffing.

## Recommendations (staged MVP)

**Highest-impact 20%:** the ingestion → normalization → DynamoDB → API → live dashboard pipeline, fully in Terraform with CI/CD and CloudWatch. That alone is a complete, defensible Cloud/DevOps portfolio project even with zero ML — build this first and get it deployed and public.

- **v1 (MVP, ~4–6 weeks part-time):** 3 feeds (abuse.ch URLhaus + Feodo, CISA KEV, AbuseIPDB enrichment on a filtered subset). EventBridge + Lambda ingestion, DynamoDB store, API Gateway backend, React globe/2D map of malicious-infrastructure geolocation with filters. Terraform + GitHub Actions + CloudWatch + Budgets alarm from day one. No ML yet.
- **v2 (~+3–4 weeks):** Add statistical anomaly detection (PyOD/Prophet) on per-category volume + spike alerts via SNS; add a DBSCAN clustering view. Add OTX for MITRE/industry context.
- **v3 (stretch):** Integrate TRAM for ATT&CK tagging of OTX report text; add LSTM forecasting *with baselines* as an explicit, honestly-labeled "experiment"; add user IP-range subscription/alerting.

**Benchmarks that should change your plan:** If you're within ~8 weeks of placement season, freeze at v1 — a polished, deployed, IaC-managed pipeline beats a half-working ML model every time. If a feed's ToS tightens or its key gets rate-limited, fall back to the always-free, no-auth sources (CISA KEV, Shodan InternetDB/CVEDB, NVD). If cloud spend ever trips your Budgets alarm, move scheduled ML from always-on to on-demand Fargate.

## Caveats
- **Legal/ethical:** Keep it non-commercial (most free tiers require this); attribute Shodan and abuse.ch data per their terms; **never publish "predicted target" claims about real named organizations** (defamation/panic risk) — keep any prediction at the aggregate category/geo level and label it clearly experimental. Respect every rate limit or you'll get key-banned mid-demo. Don't scrape endpoints faster than their stated cadence (e.g., URLhaus dumps every 5 min).
- **Why similar student projects feel shallow to interviewers:** they clone a pretty globe over fake/replayed data (the Norse trap), overclaim "AI prediction" they can't defend under questioning, and have no real infrastructure story. Your mitigations: cite real feeds, report honest metrics and baselines, foreground the cloud/DevOps engineering, and be candid about limitations.
- **Conflicting evidence noted:** A minority of papers (e.g., Siami-Namini & Siami-Namin's "ARIMA vs. LSTM") report large LSTM gains on *financial* series — results are dataset-dependent, which is exactly why you must show your own baseline comparison rather than assert LSTM superiority.
- **Freshness:** Free-tier quotas, API auth requirements, and AWS free-tier rules change often (the 2025 abuse.ch mandatory-auth switch, the Timestream LiveAnalytics closure, and the 2025 AWS free-tier restructure into 6-month/Always-Free plans are recent examples). Re-verify each feed's limits and AWS's current free-tier terms at build time.
